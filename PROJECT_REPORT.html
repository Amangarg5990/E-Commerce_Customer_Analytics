Executive Summary & Core Achievement

This report documents the design, implementation, and deployment of a full-stack Customer 360 predictive analytics platform. By modeling customer purchasing history into hierarchical BSON documents, relational multi-table JOIN latency is eliminated. In-database feature engineering is offloaded entirely to MongoDB's C++ aggregation engine before feeding machine learning models (XGBoost Churn Classifier ROC-AUC: 0.9558, Accuracy: 87.00%; K-Means Silhouette Score: 0.337). The platform is monitored through a clean, light-themed Streamlit dashboard.

1. Problem Statement & Database Architecture Motivation

In traditional third-normal-form (3NF) relational architectures, customer order history is partitioned across separate tables (Customers, Orders, Order_Items, Products). As transaction volume scales into millions of rows, analytical queries face critical bottlenecks:

  • Degraded Join Latency: Multi-table nested loop and hash joins cause queries to degrade from milliseconds to tens of seconds.
  • Memory Fragmentation: Relational rows are stored across separate disk blocks, eliminating CPU cache locality.
  • MongoDB Document Solution: By embedding orders and item arrays inside the root customer document, all data pertaining to a customer is co-located in contiguous memory pages, enabling O(1) indexed point lookups.
  • Single-Document Atomicity: Updates to customer order history and cumulative stats commit atomically without the overhead of distributed two-phase locking.

2. Dataset Overview & Cleansing Pipeline

The system ingests the UCI Machine Learning Online Retail Dataset, comprising real purchases from a UK-based giftware merchant.

  • Raw Observations: 541,909 transactional rows from Online Retail.xlsx.
  • Guest Checkout Removal: 135,080 records lacking CustomerID were pruned.
  • Cancellation Filtering: 8,905 cancelled orders (prefixed with 'C') or non-positive quantities and prices were filtered.
  • Customer 360 Synthesis: Exactly 397,884 clean purchase items were grouped into 4,338 rich Customer 360 documents.

4. In-Database MongoDB Aggregation Pipelines

Rather than pulling high-volume JSON documents into application memory, feature extraction is executed directly in MongoDB's C++ aggregation engine.

RFM & Churn Labeling Pipeline

db.customers.aggregate([
  {
    $project: {
      customer_id: 1, country: 1,
      frequency: { $size: { $ifNull: ["$orders", []] } },
      monetary: { $round: [{ $sum: "$orders.order_total" }, 2] },
      total_items: { $sum: "$orders.items_count" },
      recency_days: {
        $round: [{ $divide: [{ $subtract: [ISODate("2011-12-10T00:00:00Z"), "$last_purchase_date"] }, 86400000] }, 1]
      }
    }
  },
  {
    $project: {
      customer_id: 1, country: 1, recency_days: 1, frequency: 1, monetary: 1,
      avg_order_value: { $round: [{ $cond: [{ $gt: ["$frequency", 0] }, { $divide: ["$monetary", "$frequency"] }, 0] }, 2] },
      is_churned: { $cond: [{ $gte: ["$recency_days", 90] }, 1, 0] }
    }
  }
]);

5. Machine Learning & Predictive Modeling

5.1 Unsupervised RFM Segmentation (K-Means)

Because transaction frequency and spend are log-normally distributed, features were transformed via ln(1 + x) and scaled. An optimal k = 4 was determined, yielding a Silhouette Score of 0.337.

5.2 Supervised XGBoost Churn Classifier

To eliminate data leakage, recency_days was strictly excluded from training features. An XGBoost Classifier was trained with scale_pos_weight = 1.99 to handle class balance.
